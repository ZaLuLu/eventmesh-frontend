# EventMesh redesign plan

**Status:** implementation started with owner authorization; see [progress and verification](REDESIGN_PROGRESS.md). **Audit date:** 15 October 2026. **Scope:** this frontend checkout, all routed screen families and shared foundations. Paths and line ranges below refer to the pre-implementation audit snapshot, relative to the repository root; implementation has since moved some lines. Historical plans remain intact.

## Executive summary

EventMesh combines discovery of externally sourced events with first-party event hosting, registration, personal passes and organization operations. It already has useful domain boundaries, route splitting, permission helpers, URL filters, QR workflows and a substantial primitive library. Preserve these. The redesign should repair reliability and accessibility first, consolidate the existing system second, and simplify screen composition third.

The most urgent defect is functional: `.admin-scope` overrides canonical colors but inherits aliases already resolved against the light root. The resulting admin sidebar is white with white labels, while some workspace headings are dark on dark. Browser-computed values confirm the mismatch. Other release priorities are the public demo-registration shortcut, fabricated analytics, unlabeled inputs, inaccessible custom overlays and calendar cells, and indefinite loading states.

Keep **Geist**, the established **purple brand accent**, real event artwork, club identity, and existing light/dark capability. Neutralize canvas and chrome; purple is for actions, selection and focus, not every surface. Use compact operational tables, readable forms, a direct wallet with mandatory 3D tickets and a much shorter public home page. Do not replace the router, state stack, backend contracts or whole component tree.

**Confirmed product direction (owner clarification):** support multiple types of organizations and a general audience on laptops and mobile devices. Purple is a client requirement. Light mode is the first-use default across public and admin screens. The 3D ticket experience is mandatory and must remain a first-class interaction on both device classes. Backend capability assessment, expansion and changes are outside this redesign; preserve existing contracts and capabilities.

**Priority order:** correctness and accessibility → token/primitive normalization → navigation and discovery → registration/tickets → remaining operational and content screens → measured performance cleanup. Each phase below has acceptance gates and rollback instructions.

### Primary flows to protect

1. Discover/filter → native event detail → existing registration/profile/team/questions flow → authoritative result → issued ticket wallet; imported event → clearly labeled provider link. Do not send imported IDs into native registration.
2. Wallet → QR pass → gate scan → server-confirmed admission; offline queued scans remain distinct from confirmed check-in.
3. Organizer → create/edit draft → form builder → review/publish under existing permission rules → roster/export → certificates/announcements.
4. Staff → event selection → scan/manual entry → accepted/already admitted/wrong event/invalid/network outcome → recovery/undo where supported.
5. Public certificate lookup → verified/not found/unavailable result.

These flows are grounded in `src/app/router.tsx:123–427`, `RegisterPage.tsx:28–105`, `AdminEventWizardPage.tsx:118–150`, and `AdminCheckinPage.tsx:71–145`. Production payment processing, cryptographic trust and real-time push behavior are not confirmed.

### Accessibility release contract

Use [WCAG 2.2](https://www.w3.org/TR/WCAG22/) as the target, not a declaration of compliance. Verify keyboard operation, visible/unobscured focus, labels and errors, text/non-text contrast, reflow, status messages, dragging alternatives and target size. AA target minimum is 24×24 CSS px with applicable exceptions; **44px** is the proposed touch design target, **48px** at check-in. Normal text needs 4.5:1; large text 3:1; meaningful control boundaries/focus 3:1 against adjacent colors.

Every shared control must have a documented default, hover, focus-visible, active, disabled, pending, error and success treatment where the state applies. Success/error may belong to the surrounding form or result panel rather than changing every button into a badge. Never make an unavailable control look actionable; never remove the accessible name while pending. Reduced motion must cover JavaScript animation as well as CSS. Respect text selection for dates, addresses and ticket IDs.

## Design direction and tokens

**Direction:** light-first, purple-branded event workspace for general audiences and multiple organization types. Public pages use an index-led structure with artwork as content; operational pages use a workbench with scoped navigation, compact toolbar and data region; prose pages use a readable document column. One shared visual grammar across all three. Default to solid surfaces, 1px dividers and clear selected states. No ambient glow, animated count-up, card tilt, badge sparkle or fake telemetry.

### Organization-neutral presentation

Current campus wording is evidence of the existing implementation, not the target product boundary (`src/config/appConfig.ts:24–36`; `src/app/PublicHeader.tsx:27–50`; `RegisterPage.tsx:653–688`). Reuse existing organization/label configuration. General defaults: Organization, Organizer, Attendee, Email address and Member ID when that field is applicable. Use Discover events, Upcoming events and Your tickets in shared navigation and headings. Organization-specific deployments may explicitly choose Campus, Club or Student; retain authentic organization/event names and artwork.

Remove universal campus claims from Home, login, wallet, calendar, certificate and footer copy. Do not universally require academic terminology in frontend guidance; reflect the existing configured fields and validation rules without changing server contracts. If an existing integration only accepts academic identifiers, report that constraint accurately in its configured context rather than promising unsupported general registration. Hide irrelevant campus controls for non-campus organizations using existing configuration; avoid inventing a new tenancy/backend model.

### Mandatory 3D ticket interaction

Retain 3D ticket presentation and the existing meaningful flip/tear/admission interaction. A profile lanyard is not automatically equivalent to a ticket: preserve the actual ticket interaction and evaluate profile spacing separately. Mount the normal 3D ticket experience on both laptop and mobile; do not require an opt-in toggle to obtain the feature. Show ticket metadata and named DOM actions immediately while its module/resources load. Use a stable reserved canvas region sized to available space, not a fixed 580–660px identity stage.

Pointer, touch and keyboard users must have equivalent actions. Leave vertical page scrolling available; drag gestures are enhancements, with explicit controls for meaningful operations. Keep QR readable in an untransformed region or a dedicated Present ticket view. Animation reflects existing ticket state and cannot imply admission before the current service confirms it. Honor reduced motion with a stable pose/minimal transitions; WebGL failure has a usable static ticket fallback. Neither fallback removes the mandatory feature from the standard experience.

Measure mobile frame times and resource use; cap DPR based on device testing, reuse textures, dispose resources and suspend offscreen/hidden/settled loops. Retain existing lifecycle fixes. These changes improve reliability without replacing the required interaction.

## Screen-by-screen plan

## Risks

- **Contract parity:** main source and deployed responses may differ. Validate raw response fixtures and frontend adapters before rollout; do not extend backend scope to resolve UI assumptions. Correct F29/F30 without renaming wire fields or changing permission rules.
- **Production parity:** screenshots use local mock data and a seeded administrator; HTTP coverage, backend authorization and role-specific access are not certified. Keep presentation changes isolated from service payloads.
- **Theme inheritance/portals:** F01 can recur if aliases exist only at root or a portal escapes a scoped theme. Test computed colors, not just token source text.
- **Existing system changes:** retaining brand purple reduces churn, but dark accent contrast and new density may affect recognition. Review real artwork and long translated content before rollout.
- **Security-themed presentation:** QR signature, OTP, “cryptographically bound” and certificate guarantees require backend evidence (`docs/KNOWN_GAPS.md:16–32`; `RegisterPage.tsx:670`). Replace unsupported copy; do not imply frontend styling supplies authenticity.
- **Operational changes:** camera permission, intermittent venue networks, duplicate admission and partial queue sync require actual device/service testing. A visual pass cannot resolve admission policy.
- **Content migration:** JSX class codemods can unintentionally touch art colors or status semantics. Keep narrow transformations with reviewable diffs and adapters.
- **Mandatory 3D quality:** preserve the ticket experience on laptop and mobile; prevent canvas clipping, touch-scroll interception, QR distortion and unnecessary idle rendering. Provide equivalent DOM actions and reduced-motion/WebGL-failure fallback. Do not assume RAF is perpetually running after current fixes.
- **Library provenance:** installed package licenses do not establish the license of every copied community component. No new 21st.dev/React Bits component is approved by this plan.
- **Verification scope:** no field measurements, full screen-reader audit, production bundle baseline or cross-browser/device matrix completed in this documentation task. Do not reuse old “100% verified” claims.
